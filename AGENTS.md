# AGENTS.md

Orientation for AI coding agents working in this repo.

## What this is

Lathe is a Go CLI plus a set of coding-agent skills (the `SKILL.md` format is now a cross-tool standard — Claude Code, Cursor, Codex, Gemini CLI, opencode, Cline, Windsurf) that together generate, store, serve, verify, and extend hands-on technical tutorials. See `README.md` for user-facing docs.

The boundary is strict: **skills generate content; the CLI owns durable state.** All model work — generating, verifying, extending, answering reader questions, and authoring voices — runs in the user's **interactive** coding-agent session via user-invoked skills (`/lathe`, `/lathe-verify`, `/lathe-extend`, `/lathe-ask`, `/lathe-check`, `/lathe-tag`, `/lathe-voice`, `/lathe-work`). **The binary hosts the user's own agent; it never calls a model API itself.** It runs no `claude -p`/headless run and contains no model client. The one agent subprocess it may start is the user's own ACP agent — the one named with `lathe serve --agent <cmd>` or picked from the built-in registry in the reader's agent panel — which it runs to serve Ask, Verify, Extend and Check my work (see "Hosted agent" below); that agent does the model work under the user's own login. Don't move generation logic into Go, and don't have skills write to `~/.lathe/` directly — they call `lathe` commands (`lathe store`, `lathe verify-result`, `lathe extend-start`/`extend-commit`, `lathe check-result`, `lathe voice add`) instead. The one skill→CLI **read** path is `lathe voice show` (the active voice spec) — still consistent with the boundary: the CLI stays the sole owner of the voice files and config; the skill only asks for text.

The web buttons close the copy-paste gap without crossing that boundary. With a hosted agent they run the matching skill there over ACP (the prompt carries the skill text). Otherwise, as the fallback for agents without ACP support, when a `/lathe-work` worker session is connected (it long-polls `GET /-/work`, so `internal/queue` knows it's live), Ask/Verify/Extend **enqueue a job** the worker claims and runs in its interactive session; with no worker they fall back to the same paste-able handoff as before. The model still only ever runs in the interactive session — the queue is just an in-memory bridge between the browser and that session. The Lathe MCP server (`lathe mcp`, `internal/mcp`) is an alternate transport for the skills' **write commands**, not a way to run a model inside Go: it serves `lathe_store`, `lathe_verify_result`, `lathe_extend_start`, `lathe_extend_commit`, `lathe_tag`, `lathe_check_result` and `lathe_voice_add` as typed tools that call the same `internal/store`/`internal/voice` functions as the CLI. The skills prefer the tools when the session has them and keep the CLI instructions as the fallback.

## Build, test, run

```bash
go build -o lathe                 # build the binary
go test ./...                     # run all tests
go vet ./...                      # static checks
```

Tests are plain `go test` (no top-level runner script). The `/lathe` (`lathe`) binary built from this repo is gitignored at the repo root.

### CI gate — run before opening a PR

CI (`.github/workflows/ci.yml`) runs `mage check` on every PR and push to `main`: gofmt, `go vet`, `golangci-lint`, `go test -race ./...`, and `go build`. **Before opening or updating a PR, run `mage check` and make sure it's green** — don't push work that leaves CI red. `mage check` is the exact command CI runs, so local and CI cannot drift. CI also runs a `desktop` matrix (ubuntu-24.04 with GTK4/WebKitGTK 6 under `xvfb-run`, macOS, Windows with `CGO_ENABLED=0`): `go vet`/`go build`/`go test ./internal/desktop/ ./cmd/` with `-tags desktop`, plus an unsigned `build/darwin/package.sh` on macOS. `mage check` stays the CLI-only gate; run `mage desktopCheck` locally when you touch `internal/desktop` (needs `libgtk-4-dev libwebkitgtk-6.0-dev` on Linux).

### Visual proof — required for user-visible changes

Any PR that changes what a user sees (pages, styles, templates, browser scripts, rendered tutorial content, CLI output) must show it in the PR description, following the "Visual proof" section of `.github/pull_request_template.md`. Capture the running app with the pre-installed Playwright (start `lathe serve` against a scratch `HOME` with a sample tutorial): light **and** dark, every state you touched (including error and interactive steps), a phone viewport for layout changes, and scripts off when the change adds browser behavior with a fallback. Commit the images to the `pr-media` branch under `pr-<number>/` and embed them by commit SHA (`https://github.com/devenjarvis/lathe/blob/<sha>/pr-<number>/<name>.png?raw=true`) with alt text. Look at every shot before posting it; they catch real bugs.

`magefile.go` defines the targets (`mage fmt|fmtCheck|skills|skillsCheck|vet|lint|test|build`, and `mage check` for all of them; `mage` alone runs `check`). It's stdlib-only and build-tagged (`//go:build mage`), so it adds nothing to `go.mod`. Lint config lives in `.golangci.yml`. One-time tool install:

```bash
go install github.com/magefile/mage@v1.15.0
curl -sSfL https://raw.githubusercontent.com/golangci/golangci-lint/HEAD/install.sh | sh -s -- -b "$(go env GOPATH)/bin" v2.12.2
mage fmt                          # auto-fix formatting; mage check is read-only on fmt
```

## Architecture notes

- **`cmd/serve.go`** registers `--port` on its command's flags but stores it in the package-level `servePort` variable, which `cmd/open.go` also reads. Keep them in sync if you add new commands that need the port. It also writes `~/.lathe/serve.json` (URL/PID/started) on startup and removes it on shutdown — so it runs an `http.Server` with `signal.NotifyContext` + `Shutdown` (not bare `ListenAndServe`) to make the cleanup deferred-removal actually run on Ctrl-C/SIGTERM. The worker CLI reads that file to find the server. On startup `serve` also prints a one-line "run /lathe-work for live mode" hint (a nudge, not a spawn). With `--agent <cmd>` (else the agent picked in the web UI, `config.Agent()` looked up in `internal/agents`), `serve` calls `srv.SetAgent(cmd)` to host that ACP agent, and `defer srv.Close()` stops it on shutdown.
- **`internal/serve/server.go`** uses Go 1.22+ method-and-pattern routing (`mux.HandleFunc("GET /{slug}/", …)`). `safeTutorialPath` defends against path traversal by checking the joined path stays under `tutorialsDir` — preserve that check on any new route.
- **Agent vs. queued vs. handoff (verify/extend/ask).** The Go binary spawns no `claude` subprocess; the only exception is the hosted ACP agent, described below, which `askViaAgent`/`jobViaAgent` try first (a start failure falls through with a `notice`). The web POST endpoints (`internal/serve/{ask,verify,extend}.go`) validate + conflict-guard + `sameOrigin`-check, then branch on worker presence (`queue.WorkerConnected()`): with a worker connected they `Enqueue` a job and return `{"mode":"queued","jobId":…}` (`writeQueued`); with none they return `{"mode":"handoff","command":"/lathe-… <slug> …"}` (`writeHandoff`) and the templates render a copy-to-clipboard panel. Either way the work runs in the user's interactive session via the matching skill (driven by `/lathe-work` in the queued path, or pasted by the user in the handoff path), which calls back into the CLI to mutate state: `/lathe-verify` → `lathe verify-result <slug> --status verifying` (in-flight badge) then a terminal `--status verified|failed|skipped [...]`; `/lathe-extend` → `lathe extend-start` (reserves the part, prints its filename, sets `extending`) then `lathe extend-commit`. **Status is set by the skill, never by the web/CLI button or the queue** — that's deliberate, so an unclicked button (or an enqueued-but-unclaimed job) can't leave a badge stuck at `verifying`/`extending`.
- **Code snapshots (`internal/store/code.go`).** `/lathe-verify` `git init`s its scratch dir, commits + tags each part that passes (`part-NN`, the part filename minus `.md`), and passes `--code <scratch>` to `lathe verify-result` (with `verified`/`failed` only; `--no-save` opts out). `store.SaveCode` `git clone`s it into `<tutorial>/code/` — clone, not copy, so untracked build output stays behind — building beside the destination and swapping in only when complete, and drops the dangling `origin` remote. The status is recorded *before* the snapshot is saved, so a snapshot error can never strand the badge at `verifying`. `store.Store` removes `code/` on re-store (it would describe the old content). The reading page shows a `.code-snapshot` provenance `<details>` with `git -C <path> checkout`/`diff` commands when the current part has a tag (`codeSnapshotFor` in `server.go`); `store.CodeTags` reads loose refs + `packed-refs` directly, so rendering never shells out to git. The path is shown with `~` for the home dir. The `code/` dir is never served: `handlePart` only renders declared parts.
- **Hosted agent (`internal/acp` + `internal/serve/agent.go`/`agent_http.go`, `lathe serve --agent`).** `internal/acp` is a minimal Agent Client Protocol client: newline-delimited JSON-RPC 2.0 over the agent's stdio (`conn.go`), plus `initialize` (protocol version 1, advertising `fs.readTextFile`, `fs.writeTextFile` and `terminal`), `session/new`, `session/prompt`, the `session/update` stream, `session/request_permission` and `session/cancel` (`client.go`). `acp.Start` runs the configured command through `/bin/sh` from the tutorials dir. **Per-job policy (`policy.go`, `fs.go`, `terminal.go`).** Every session gets an `acp.Policy` via `Client.SetPolicy` (read roots, write roots, exec roots); `fs/read_text_file`, `fs/write_text_file` and `terminal/create|output|wait_for_exit|kill|release` are answered only inside it, and a session with no policy is refused everything. Paths must be absolute and are judged after resolving symlinks (a dangling link is refused), so `..` and links can't escape a root. Refusals are JSON-RPC `-32602` errors whose message names the allowed roots, so the agent can correct itself. Job policies: `AskPolicy` (read the tutorial dir only), `VerifyPolicy` (read tutorial + scratch, write/run in scratch), `ExtendPolicy` (Verify + write the tutorial dir), `CheckPolicy` (read tutorial + learner workspace, write/run only in a scratch copy). Ask uses `AskPolicy`, Verify `VerifyPolicy`, Extend `ExtendPolicy`, Check my work `CheckPolicy`. Commands run in their own process group (killed on `terminal/kill`/`release` and on `Client.Close`); a command line with no `args` runs through `/bin/sh -c`. This is policy enforcement in Lathe, not an OS sandbox: it bounds the cwd, not what a permitted command then does. Each handled (or refused) request is reported to the session handler as an `acp.Activity` (the panel shows reads, writes, commands with their output tail, and "Blocked by Lathe" refusals). **Isolation (`isolation.go`):** an agent may ignore the client methods and keep using its own tools, which Lathe can't see. `Client.Isolation()` compares the agent's completed tool calls (kind read/edit/delete/move vs. execute) with the fs/terminal requests it actually sent: `enforced`, `soft` (it used its own tools; its own permission prompts are the boundary) or `unknown` (no file access yet). `/-/worker` reports it as `agent.isolation` and the panel header shows it as a pill. `internal/acp/acptest` is a scripted fake agent for tests and demos; prompt markers `[permission]`, `[crash]`, `[slow]`, `[tool]`, `[owntool]` and `[read:PATH]`/`[write:PATH]`/`[run:CMD]` (which call the client's fs/terminal methods) choose its behaviour, and `Agent.Plan` makes it report a plan and one tool call per step. In the server, `agentHost` starts the agent in the background, restarts it on the next ask after it exits, and keeps one ACP session per `slug/part` (its cwd is the tutorial dir). The first prompt in a session carries the `/lathe-ask` skill text (frontmatter stripped) and the same invocation the handoff would paste; follow-ups send only the question. `POST /-/ask` prefers the hosted agent, then a `/lathe-work` worker, then the handoff, and returns `{"mode":"agent","runId"}`. The panel then streams `GET /-/acp/{id}/events` as SSE: `chunk`, `html`, `tool`, `permission`, `permission_resolved`, then `done` (with the answer rendered to HTML) or `error` (with the handoff command). While the prompt runs, the server re-renders the answer so far about every 200ms into an `html` event, so the panel shows formatted markdown as it streams. Each new snapshot empties the previous one, which replays as `html_stale`, to keep memory and replays small. A tool call, a thought, or a new `messageId` starts the next message chunk as its own markdown block, because real agents split one turn into several messages. Answers get compact `.ask-rich` typography (drawer-scale headings, and tables and code that scroll). Each event's index is its SSE id, so a reconnect resumes from `Last-Event-ID`, and a finished run answers a reconnect with 204 so EventSource stops. Permission prompts are answered via `POST /-/acp/{id}/permission`; an unanswered prompt resolves to `cancelled` after 10 minutes. `POST /-/acp/{id}/cancel` sends `session/cancel`. Both mutations are `sameOrigin`-checked. Only one answer per part streams at a time (409 otherwise). A start failure or a crash mid-answer always ends in the copy-paste handoff with a notice, and `/-/worker` reports `agent.state` (`starting`/`ready`/`down`) for the panel header. **Verify/Extend (`agent_jobs.go`).** `POST /-/verify|extend/{slug}` prefer the hosted agent too (`jobViaAgent` → `startJob`): one job per tutorial at a time (`jobKey`; a second verify or extend gets 409), a **fresh session per run** whose cwd is a Lathe-made scratch dir (`os.MkdirTemp`, symlinks resolved; Verify) or the tutorial dir (Extend), under `VerifyPolicy`/`ExtendPolicy`. `jobPrompt` frames the hosted run (use this scratch dir instead of `mktemp -d`, record via the `lathe_*` MCP tools, keep a plan, finish with a report) and embeds the skill text (`lathe-verify`, or `lathe-extend` + `lathe`), then the handoff invocation. The skill still sets every status itself; the server never does, except to **undo** one: the run's `after` hook (run before the final event, so a browser polling on `done` sees it settled) drops the session's policy, calls `settleJob` — `store.CancelVerify` (restore the last result, like `lathe verify-cancel`) or `store.CancelExtend` (delete the unregistered reserved part, clear `pending_part`, restore the last result) when the run left the tutorial in flight — and removes the scratch dir (after `verify-result --code` has cloned it). Progress streams over the same SSE endpoint: `plan` (full entry list), `tool` (id/title/status/kind), `tool_update`, `activity`, permissions, the report as `html`, then `done` (with `message` when a status was restored) or `error` (with the handoff command). The reading page has `#verifyLive`/`#extendLive` slots **outside** the regions the status poller swaps; `latheAttachJob` (layout.html) fills them, with Stop (`/-/acp/{id}/cancel`) then Dismiss. The page and `/-/status` carry the running job (`AgentRun` → `#statusPoll[data-run-id]`, `run`) so a reload or another tab reattaches. `POST /-/verify/{slug}/cancel` (and `/-/extend/…`) cancels the slug's job and waits for it to settle; `lathe verify-cancel` calls it via `serve.json` before restoring the status itself. `agentHost.close` waits (≤10s) for cancelled runs to settle on shutdown. `/lathe-work` and the copy-paste handoff remain the fallback. **Lathe MCP per session:** `session/new` carries `mcpServers` with one stdio entry, `lathe` → `<os.Executable()> mcp --slug <slug>` with `HOME` passed through (`latheMCP` in `agent.go`), so the agent's tools write the same `~/.lathe`. A `--slug`-scoped server offers only the per-tutorial tools (`lathe_verify_result`, `lathe_extend_*`, `lathe_tag`), defaults their `slug` to the scope and refuses any other; `lathe_store`/`lathe_voice_add` are unscoped-only. Tool failures come back as `isError` results (so the agent can fix its call); unknown tools are JSON-RPC errors. Arguments are decoded strictly, so a misspelled field is an error. `acp.Conn.Wait` lets the server answer in-flight calls after stdin closes. Billing: see the README note. Claude's adapter is Agent SDK use, which currently draws on the subscription, but the planned metering is paused, not cancelled.

## Conventions

- One cobra subcommand per file in `cmd/`, registered via `init()` calling `rootCmd.AddCommand(...)`.
- Errors flow up through `RunE`; the root `Execute()` exits non-zero on any error.
- Keep `internal/` packages free of cobra imports — they should be usable from tests directly.
- Skills are markdown files, all checked into `.claude/skills/<name>/SKILL.md` (`lathe`, `lathe-verify`, `lathe-extend`, `lathe-ask`, `lathe-check`, `lathe-tag`, `lathe-voice`, `lathe-work`) and user-invoked in an interactive session. They **are** embedded in the binary (via the generated `internal/skills/data/` mirror, so `lathe skills install` works post-`brew`/`go install`) — but the binary still spawns no `claude`: embedding ships the skill *text*, it doesn't run a model. Keep that distinction.
- Status values are an enum (`store.Status`): `unverified` (default after store; renders no badge), `verifying`, `verified`, `failed`, `skipped` (required tool not installed — not a failure), `extending`. New states should be added there and reflected in `cmd/list.go` `statusBadge`, the `{{define "badge"}}` partial in `components.html`, and the `--badge-*` tokens + `.badge.<status>` rule in `styles.css` (see "how to add a new status" in `docs/design-system.md`).

## Things to avoid

- Don't call a model API from Go, and don't spawn any agent other than the one the user configured with `lathe serve --agent` or picked in the agent panel (registry entries only). Hosting the user's agent over ACP is allowed; becoming a model client is not. ACP fs/terminal requests are answered only within the session's `acp.Policy`; never answer them without one, and keep the panel showing what was read, written, run or refused.
- Verification is **opt-in / on-demand**: it runs only when the user asks (`/lathe-verify <slug>` in their session — surfaced by the `lathe verify` command, the `--verify` flag on `lathe store`, or the "Verify this tutorial" web button, which runs it on the hosted agent, else enqueues a job for a connected `/lathe-work` worker, else hands off that command). Storing never auto-verifies; the default status is `unverified`. Don't re-introduce a Go-side verifier subprocess. Don't add a `lathe status` *read* command — status is surfaced via `lathe list` and the web UI (the `verify-result`/`extend-*`/`tag` commands are write-only state mutations for skills).
- Don't add tutorial editing or sharing commands without checking with the user — the v1 scope is deliberately narrow. (Deletion is supported via `lathe rm <slug>` and the `×` button on the web list page; both go through `store.Delete` / `safeTutorialPath`.)
- Don't have the verify/extend skills edit `metadata.json` or `verify-result.json` directly — they call `lathe verify-result` / `lathe extend-commit` (or the matching `lathe_*` MCP tools) so the binary stays the sole writer of durable state. Put new write logic in `internal/store` (see `ops.go`) and call it from both the cobra command and the MCP tool, so the two transports can't drift. The verify skill is read-only with respect to the tutorial markdown.
- Don't add OS-level sandboxing (sandbox-exec, Docker) for verification unless explicitly asked. In the interactive session, isolation is by instruction: the `/lathe-verify` skill builds in a fresh `mktemp -d` scratch dir under the user's normal interactive permission model. For the hosted agent, the scratch dir is one Lathe makes per run, and Lathe enforces a per-job `acp.Policy` on the ACP fs/terminal methods — policy enforcement, not sandboxing — and reports "soft" isolation when the agent uses its own tools instead.

## Commit style

Conventional commits (`feat:`, `fix:`, `chore:`, `refactor:`) — match the existing log. Keep subject lines short and imperative. Tests typically land in the same commit as the code they cover.
